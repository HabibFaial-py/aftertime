# Phase 4 #014H-1: dormant claim and inbox preparation

## Result

Claiming and pending discovery remain **unavailable**. A transactionally consistent current-confirmed-email authority has not been demonstrated for Supabase Auth email changes, confirmations, deletion or reassignment. The previously reported PostgreSQL row-lock conflict does not prove that every provider path participates in the proposed transaction; a localhost redirect after confirmation is not proof of success or failure. A local Auth stub cannot establish managed-provider guarantees. Implementing a callable claim or discovery RPC now would bypass the user's explicit security condition.

## Changes prepared

- Draft migration `0008_dormant_claim_preparation.sql` checks that the validated `CHECK (false)` gate and direct-table foreign key from 0006/0007 are present, and that the anticipated claim/discovery functions do not exist. It aborts if these prerequisites drift. It creates a partial index for a possible future pending lookup, restricted to rows whose `claimed_at` is null; previously claimed accounts that were later deleted therefore do not enter the index. It does not add any RPC, data, grant or policy, alter the feature gate, or authorize an email lookup. The index is a preparatory candidate and must be reviewed against the final query and privacy policy: if data is later enabled, it also stores normalized email values in an index.
- The existing FastAPI inbox and claim endpoints still return 503 after authentication, even if `DIRECT_CAPSULES_ENABLED=true`; the default-disabled flag continues to return 404 before authentication or database access. They now reject unexpected query parameters and request bodies. No JWT email, client email or user ID is used for these endpoints, and neither endpoint queries the database.
- Strict proposed response models allow only capsule `id`, `created_at` and `unlock_at`, rejecting body, title, email, sender name and other extra fields. They define a future safe projection, not proof of an implemented successful endpoint. Seven-day expiry remains a structural relation in 0006; no RPC currently enforces eligibility at claim time. The separate direct table and existing capsule-then-invitation ordering remain unchanged.

## Local verification

- Backend: `python -m pytest -q` from `services/api` passed **200 tests**, with the existing Starlette TestClient deprecation and short synthetic HMAC-key warnings. Added tests verify minimal models, rejected identity overrides and bodies, absence of JWT-email authority, and two concurrent authenticated HTTP claim attempts returning 503 without database calls.
- On a disposable loopback-only PostgreSQL 18 cluster, migrations 0001-0008 were applied locally in order, with the 0006 foundation tests run before 0007. Existing self-creation, direct draft, cancellation/reveal race and new dormant-claim checks passed. Two separate local SQL sessions concurrently attempted the absent claim function; both failed because the RPC does not exist. The cluster was stopped and removed. These are gate tests, not claim-race or managed Auth tests.
- `test_dormant_claim_preparation.sql` also checks the index, validated gate, RLS, effective table privileges for application roles and the absence of the anticipated RPC names. It is **local disposable PostgreSQL only**; its database-name/role guard is not enough to make it safe on Supabase. Previous direct SQL tests temporarily remove the gate for synthetic testing and must likewise never run on a shared database.
- Python syntax and Git whitespace checks passed. No Supabase request, hosted migration or original database modification occurred.

## Required before claim implementation or activation

1. Verify actual supported Auth initiation and every confirmation-stage transaction, pending email-change flags, current-confirmed-email semantics, account deletion and reassignment, and the effective locking/privilege boundary in an isolated project under separate authorization. Select and review a protocol that remains valid through the claim transaction commit; if the provider does not support it, use a separately approved identity design. Never rely on the JWT email or a preflight check.
2. Implement service-only claim and discovery in one transaction each, deriving the UUID from the verified backend session. Enforce confirmed current matching email, no pending email change, capsule cancellation/deletion, 168-hour expiry and terminal historical state using database time captured after relevant waits. Preserve a reviewed Auth/profile/capsule/invitation lock ordering, including capsule before invitation for mutations. Define the authorized same-user retry rule and deny competing claimants.
3. Add real local SQL tests for correct claim; wrong/unconfirmed/deleted account; pending email change; expiry boundary; cancellation; duplicate same-user and cross-user claims; and concurrent claim/claim, claim/cancel, claim/email-change and account-deletion operations in both orders. Those eligibility tests are **not implemented or passed** here because there is no safe claim function to exercise. Isolated provider tests are still required beyond a local stub.
4. Verify effective client/service privileges, self/direct isolation and the safe pending projection with actual SQL calls. Add abuse limits, idempotency, revocation and approved mailbox-reassignment policy. Only after security review and separate authorization may an activation migration consider replacing the 0006 gate.
