## Encryption and transaction review

The helper generates a canonical encoding of 32 random secret bytes and returns its SHA-256 digest alongside AES-256-GCM ciphertext and a random 12-byte nonce. The 32-byte key must be passed in by a trusted caller; it is neither configured nor persisted by this code. GCM authenticates a versioned, unambiguous encoding of job, invitation and capsule UUIDs, key ID and normalized recipient address. A changed key, nonce, ciphertext or context fails authentication. The result masks nonce, ciphertext and digest in its normal representation; the secret is temporarily present in process memory and can be explicitly retrieved from the decrypted object. Python cannot promise memory erasure. Random samples and tests do not prove randomness.

The SQL function inserts the capsule, invitation digest, nonce reservation and encrypted job in a single PostgreSQL function transaction. A failure rolls back all four; it returns only ID and timestamps. The real call currently fails and rolls back at `CHECK (false)`. Fixture copies demonstrate successful inserts and failures without altering that gate. The database cannot verify that caller-supplied ciphertext is valid GCM, that its plaintext corresponds to the supplied digest, or that a key ID identifies the intended key. The existing Python helper generates matching values, but no reviewed repository or application path joins it to the RPC, and no real delivery path verifies the digest. Keep it unwired until that integration and its tests are complete.

Nonce reservations have a `(key_id, nonce)` primary key and survive invitation/job deletion; committed duplicates under the same ID are rejected. This is not a global guarantee: encryption happens before reservation; random collisions, parallel or failed attempts, distinct IDs referring to the same key, independent databases, backup restores and reservation loss can reuse a nonce. A future production design must specify key uniqueness across environments and restores, safe reservation/allocation before encryption, key rotation and per-key usage limits; database uniqueness alone is insufficient. The nonce ledger also grows and needs an explicit lifecycle that never permits reuse under a retained key.

The new SQL stores only digest, nonce, key identifier and ciphertext for the invitation secret; it receives no plaintext secret or key from the helper. The database still stores the intended email and capsule body in plaintext, as the existing schema requires. Because a privileged caller can submit arbitrary bytes, SQL cannot prevent a malicious or faulty caller from putting secret material into other fields. No new code logs secrets or exposes them in public responses, but external logging, error reporting, SQL parameter logging, transport, future callers and delivery have not been verified. Digests, ciphertext, recipient addresses and metadata remain sensitive. SQL constraints clear ciphertext in terminal states, but physical copies, WAL and backups need a retention policy and are not immediately erased.

## Remaining blockers and exact next step

Keep all gates in place. No managed key provisioning, rotation, restore-safe nonce allocation, key destruction or delivery worker exists. Lost-response handling is not an idempotent success protocol. Cancellation, deletion, revocation, expiry and claim do not yet coordinate with an outbox worker; real delivery must recheck eligibility, verify the decrypted secret's digest and handle lease/retry races without promising exactly-once delivery. Managed Auth/session behavior, deployed grants, PostgREST transactions, rate limits, abuse controls, retention, and operational logging remain unverified. Current bearer-secret claim behavior does not verify that the claiming account owns the intended email; this conflicts with the repository's stated intended-recipient verification requirement and needs an explicit security decision before activation.

**Next development step:** in a separately scoped dormant task, design and test restore-safe per-key nonce allocation and managed-key lifecycle, then implement an unwired trusted creation adapter that binds one generated secret, digest, AAD and encrypted job into the single RPC call; include local end-to-end rollback, mismatch, retry and leakage tests. Do not enable the feature or delivery in that task without separate authorization and the remaining security review.
