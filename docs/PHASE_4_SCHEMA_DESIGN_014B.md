# Phase 4, Prompt #014B — direct-capsule schema and security design

**Status: design proposal only.** The user-proposed MVP rules in this document are the design inputs. All new fields, constraints, limits, functions and behavior below are proposals for review, not existing features or executable migration instructions. No SQL was executed, Supabase contacted, or Auth locking behavior verified. A subsequent migration requires explicit approval and isolated verification.

## 1. Verified baseline and compatibility boundary

Migration 0001 has one `recipients` row per capsule (`capsule_id UNIQUE`), normalized nonblank `intended_email`, nullable `user_id` referencing `profiles` with `ON DELETE SET NULL`, optional token hash/expiry/revocation, and claim/open timestamps. Relevant existing checks are:

1. `(invite_token_hash IS NULL AND invite_expires_at IS NULL) OR (invite_token_hash IS NOT NULL AND invite_expires_at IS NOT NULL)`.
2. `invite_revoked_at IS NULL OR invite_token_hash IS NOT NULL`.
3. `user_id IS NULL OR claimed_at IS NOT NULL`.
4. `invite_token_hash IS NOT NULL OR claimed_at IS NOT NULL`.
5. `opened_at IS NULL OR (claimed_at IS NOT NULL AND opened_at >= claimed_at)`.
6. `claimed_at IS NULL OR invite_token_hash IS NULL OR claimed_at < invite_expires_at`.
7. `claimed_at IS NULL OR invite_revoked_at IS NULL OR claimed_at < invite_revoked_at`.

The optional 32-byte token hash is unique. A previously claimed row may have a null `user_id` after account deletion. The fourth check specifically prohibits tokenless pending rows. The first and second prevent reusing the token expiry/revocation columns for a tokenless pending lifecycle. Constraint names must be identified from the actual deployed catalog in a separately authorized inspection; migration 0001 did not explicitly name these checks. Do not assume PostgreSQL-generated names across environments.

Capsules store owner, title, body, unlock time, cancellation and deletion timestamps; their 90-day and cancellation-before-unlock checks remain. RLS is enabled with no client policies on six app tables, client-role grants are revoked, and `service_role` has privileged table access. Existing self RPCs 0003–0005 are postgres-owned SECURITY DEFINER with empty search path and service-role EXECUTE. The self create checks Auth confirmation and creates a bound self recipient. Self reveal/cancel require owner and recipient to be the same bound user with token fields null. Existing self listing filters owner ID, not a capsule type. Profile provisioning 0002 runs on Auth-user insert; it does not implement direct claims. `current_user` verifies JWT and supplies a UUID, not a current verified email.

The existing owner list and self RPC predicates make an explicit direct/self boundary essential. A direct row must never become eligible for a self-only function, including accidental self-addressing or historical/unbound rows. Keep existing route responses and self behavior; any new type filter must be added and regression-tested as part of the implementation plan rather than assumed compatible.

## 2. Proposed representation and exact constraint changes

The following is a design choice to review, not executable DDL:

- Add `capsule_kind` with only `self`/`direct`, nonnull; existing legitimate self capsules are backfilled as `self` after a pre-migration inventory. Add an enforceable unique key on `(id, capsule_kind)` for a composite foreign key.
- Add matching nonnull `recipient_kind` and a composite FK `(capsule_id, recipient_kind)` to the capsule key, retaining `UNIQUE(capsule_id)` and `UNIQUE(id, capsule_id)`. Existing self insertion must still create a self row, including migration 0003's insert that does not name new fields. Defaults, backfill and constraints must be coordinated. Review pre-existing non-self/token rows before classification: **abort migration for any ambiguous legacy row**, rather than silently classifying it as self.
- Add `direct_invited_at`, `direct_expires_at`, and `direct_revoked_at`, nullable for self rows. For direct rows require invitation timestamps, `direct_expires_at = direct_invited_at + 168 hours` in UTC, direct token fields null, no claimed timestamp after expiration or after/equal revocation, and no binding without `claimed_at`. Self rows require these direct fields null. Cancellation is represented by the capsule's existing `cancelled_at`, not a second competing flag. A separate direct revocation field preserves the legacy token-revocation check.
- Replace **only** check 4 with a named equivalent conditional rule: a null token hash is allowed without `claimed_at` only for `recipient_kind = direct`; otherwise preserve the original requirement. Keep checks 1–3 and 5–7, token-hash length/uniqueness, one-recipient uniqueness and FK semantics. The new kind/state checks must additionally ensure direct invitations do not use legacy tokens in this MVP. Do not weaken legacy token constraints. Review exact handling of previously existing token-backed rows; this MVP does not create, claim, or expose them.
- Enforce immutable `direct_invited_at` and expiry through service-only operations and restricted privileges; a CHECK alone does not make values immutable. Set invitation time and expiration together at creation from one post-lock database `clock_timestamp()`; seven days means **168 elapsed hours**, not client calendar days. Add an index for normalized intended-email pending discovery, designed after evaluating selectivity, privacy and query plans. It must not grant client access or reveal address existence.

The self reveal/cancel functions must be revised in a new migration to require `capsule_kind = self` and a matching self recipient; preserve their existing signatures, projections, timing and idempotency. The current owner listing must likewise explicitly filter self when new direct rows exist, preserving its mobile contract. This compatibility change needs backend and SQL tests; simply tagging new direct rows is insufficient. Direct reveal must never allow sender access, even if an address resolves to that sender. Reject self-recipient claims as a generic unavailable outcome and require `requester_id <> owner_id` at the database authorization point. The discriminator is the primary separation; a sender/recipient inequality is additional defense, not a substitute.

## 3. Proposed states and transitions

States are derived from committed row facts and one captured database time, not an independently mutable status string. Precedence is: (1) cancelled/deleted, (2) historical unbound claim, (3) valid bound claim, (4) revoked pending invitation, (5) expired pending invitation, (6) pending. A deleted capsule is unavailable rather than an invitation state. No worker is necessary merely to mark expiry.

| State | Required facts | Allowed transition and result |
| --- | --- | --- |
| **Pending** | Direct row, `claimed_at`/`user_id`/`direct_revoked_at` null, no capsule cancellation/deletion, database time strictly before expiry | Verified intended recipient may claim once; sender may revoke pending invitation or cancel the capsule while cancellation is eligible. |
| **Claimed** | `claimed_at` before expiry and bound `user_id`; capsule not cancelled/deleted | Bound UUID may list/reveal when otherwise eligible. Seven-day deadline no longer revokes the claim. Sender may cancel before unlock. |
| **Expired** | Unclaimed, unrevoked and database time at or after expiry | No discovery or claim. Terminal for this invitation; a new invitation/reissue is outside this slice unless separately designed. |
| **Revoked** | `direct_revoked_at` set before a claim, with no cancellation/deletion | No discovery or claim. Terminal for this invitation. A standalone sender-revoke operation is optional; the initial design may only need cancellation. |
| **Cancelled** | Capsule `cancelled_at` nonnull | Deny pending discovery, claim, recipient list and reveal whether previously pending or claimed. Cancellation is permanent and overrides claim/expiry. |
| **Account-deleted historical** | Previously claimed direct row with `claimed_at` nonnull and `user_id` null after `ON DELETE SET NULL` | No discovery, claim, rebinding or reveal. Retain or delete under a separately approved retention policy; never grant to a new owner of the address. |

Creation produces pending only. Claim does not require unlock; reveal does. Pending expires after seven days even if unlock is later. Claim at exact expiry is denied; cancellation at exact unlock is denied; reveal at exact unlock is allowed. `claimed_at`, cancellation and expiry decisions use database time captured after relevant locks. A user cannot claim their own direct capsule. Revocation after claim, reissue, account deletion retention and sender-visible claim state are not silently invented here.

## 4. Authoritative verified email and account lifecycle

At request time FastAPI verifies JWT signature, issuer, audience, expiration and UUID subject. The direct-inbox and claim RPC receive only that subject from the trusted backend; no client-supplied email, recipient UUID or sender ID is authoritative. **Proposed Auth source:** inside a privileged database operation, read `auth.users` for the subject, requiring a current nonblank normalized email and appropriate confirmed-email state; compare to `recipients.intended_email`. Do not trust a JWT email merely because the token was signed, since it can be stale. The existing self-create query checks `email_confirmed_at`, but this alone has not been proven sufficient for all Supabase pending email-change states.

For pending discovery and claim, require an atomic identity snapshot that cannot become invalid between comparison and binding. The candidate approach is to acquire a lock on the relevant Auth user row, re-read confirmed-email state, and retain it through transaction completion. **This is a hypothesis, not a guarantee:** verify the actual Supabase Auth change, confirmation, deletion and reassignment transactions, field semantics, locking modes, lock order and privileges. If that cannot be established, do not enable claiming; use a separately designed provider-supported verification mechanism and fail closed. Service-role/PostgREST requests have no end-user `auth.uid()` in this architecture; requester identity is a trusted backend assertion, not proof the database can independently derive from that call.

After a successful claim, the claimed `user_id` is the access principal, not the current owner of the mailbox. Proposed MVP policy: an ordinary later verified email change does not reassign or remove a claimed capsule from that UUID; it never permits a new mailbox owner to claim it. Account deletion removes the binding through the existing FK and produces the historical terminal state, subject to approved retention/deletion requirements. A never-claimed invitation addressed to a reassigned mailbox is materially different: current verified-email matching alone cannot prove it belongs to the same natural person who held the address when the sender created it. **Policy decision and risk:** either accept verified control at claim time with explicit consent and a short expiry, or require a stronger out-of-band proof; the latter needs a new design. Do not claim the former prevents reassignment risk.

## 5. Transaction, lock order and race semantics

Proposed partial order when an operation needs these objects: **admission/rate-limit guard → Auth identity row (when needed) → profile row (when needed) → capsule → recipient → future job rows**. Lock multiple rows of a type in deterministic UUID order. Existing self paths and Supabase Auth internals do not establish this whole order: verify actual FK, trigger, profile cascade and Auth lock behavior before adopting it. Never hold external network calls or prompts inside a database transaction. If the platform cannot support a safe lock order, revise the design before implementation.

- **Create:** verify sender eligibility, consume admission, atomically insert direct capsule and pending recipient, setting database creation/invitation time and seven-day expiry. Do not inspect recipient account existence. The single transaction cannot leak a partially created recipient. Decide whether an Auth/profile check locks rows first, preserving safe interaction with account deletion.
- **Pending discovery:** in a single short transaction establish a current verified-email snapshot under the verified identity protocol, then select bounded minimal pending metadata without body/title. Capture one database time; compare `now < direct_expires_at`. Locks must prevent a concurrent Auth email change from making the authorization snapshot stale before metadata is returned. Do not claim automatically. Confirm actual isolation and Auth locks before promising this.
- **Claim:** acquire verified Auth/profile identity as above, then lock capsule and recipient, re-read current state and compare confirmed normalized email. After waits capture database time and require pending, `now < expires`, not revoked/cancelled/deleted, subject not sender. Atomically bind UUID and `claimed_at`. Concurrent claimers cannot both acquire binding. A subsequent matching claimed repeat follows the retry rules below, not an expiry-based re-claim.
- **Cancel:** derive sender from verified JWT, lock capsule then recipient, recheck direct kind, owner, deletion and `created_at <= now < unlock_at` after waits. Set cancellation and invalidate an unclaimed invitation in the same transaction. Claimed rows remain historically bound, but the cancelled capsule is inaccessible. Concurrent claim/cancel serializes: cancel committed first causes claim denial; claim committed first does not prevent an eligible cancellation. No notifications or deliveries exist in this slice.
- **Reveal:** lock capsule then recipient, verify direct kind, claimed recipient UUID, `requester != owner`, noncancelled/nondeleted state and any required account-liveness conditions. Capture database time after locks; only then select body if `now >= unlock_at`. Cancellation committed first prevents a later reveal. A reveal committed before a later deletion cannot recall bytes already delivered; a new cancellation at/after unlock is ineligible.
- **Deletion and changes:** design Auth-user deletion/profile cascade and direct account deletion to follow a compatible order; claim/reveal must not race against email changes, deletion or binding invalidation. A trigger or FK path outside this order can deadlock. Resolve deadlocks or serialization failures fail-closed, with no leaked body, and use explicit tests instead of assuming row locks suffice.

PostgreSQL `READ COMMITTED` and PostgREST RPC transaction behavior, `clock_timestamp()`, row-lock compatibility and lock visibility must be verified in the target setup. Boundary comparisons above are design intent, not a test result. Use no external clock parameter in production functions.

## 6. Service-only RPC interface proposal

All functions are new, narrowly projected, database-time-authoritative, with `SECURITY DEFINER`, a reviewed owner, empty `search_path` and fully qualified objects. Revoke `PUBLIC`, `anon`, and `authenticated` EXECUTE; grant only `service_role` as necessary. Verify schema USAGE, owner and inherited/default role privileges in the deployed environment. No client may call a function by pretending to be service role, and no routine should return body except authorized reveal. Suggested signatures below are conceptual, not executable SQL:

| RPC | Arguments from trusted backend | Output and responsibility |
| --- | --- | --- |
| `aftertime_create_direct_capsule` | sender UUID, title, body, normalized intended email, unlock timestamp, approved idempotency key | `{id, title, created_at, unlock_at}`; atomic create, same response shape irrespective of recipient existence. |
| `aftertime_list_direct_sent` | sender UUID, bounded cursor/limit | `{id, title, created_at, unlock_at}`; sender-owned metadata only, no recipient-existence or claim-state signal. |
| `aftertime_list_direct_pending` | requester UUID, bounded cursor/limit | `{id, created_at, unlock_at}` only after verified-current-email authorization; no sender-written title, body, email, token or account-existence lookup parameter. |
| `aftertime_claim_direct_capsule` | capsule UUID, requester UUID | `{id, created_at, unlock_at}` after transactional current-email and state checks; no body/title. |
| `aftertime_list_direct_received` | requester UUID, bounded cursor/limit | Claimed recipient metadata `{id, title, created_at, unlock_at}` only for the bound user and uncancelled/undeleted capsule. Server-computed display status may be added separately and is never authority. |
| `aftertime_reveal_direct_capsule` | capsule UUID, requester UUID | `{id, body}` only after claimed-recipient, not-sender, no-cancel/delete and database-time checks. |
| `aftertime_cancel_direct_capsule` | capsule UUID, requester UUID | `{id, cancelled_at}` after owner and time checks, atomically preventing outstanding claims; generic zero-row denial. |

If standalone pending revocation is approved, add a narrowly scoped sender-only revoke RPC; it is not the same as cancelling a claimed capsule. Function names, pagination, owner privileges and exact errors require final schema review. Capture after-lock wall-clock time, fixed generic errors and avoid logging parameters, emails, bodies or raw Auth records. Run statements via one transaction per operation; independent queries cannot implement the race-safe claims above.

## 7. Authorization, visibility and response design

- **Sender:** authenticated owner may create and view own sent metadata and cancel before unlock. Sender cannot reveal direct content. Successful creation must have equivalent response shape/status for registered, unregistered, confirmed and unconfirmed recipient addresses. A response must not reveal whether a recipient account exists or whether it has claimed; do not expose recipient email, claimed state, detailed failure reasons, notifications or timing-derived account lookup results to sender. Network timing cannot be made perfectly indistinguishable; measure and minimize observable differences.
- **Recipient pending:** only the matching currently confirmed email may discover pending IDs, creation and unlock timestamps. No sender-written title, body or sender-provided free text is returned. A sender identity is omitted in this minimal projection pending separate review, since display names are user-controlled. Do not expose a public lookup by arbitrary email. Pending IDs authorize nothing by themselves.
- **Recipient claimed:** only the bound UUID can list metadata and explicitly reveal at/after the database time; sender cannot. Decide whether sender-written title becomes visible immediately after claim; the proposed claimed-list projection does so but body remains withheld. A session with an old email is not allowed to claim after a confirmed email change just because its JWT is valid. Claimed access remains UUID-bound under the proposed policy above.
- **Unauthenticated/wrong user:** fail closed, generic unavailable/not-found for direct IDs and indistinguishable 401 for invalid authentication. Rate-limit responses should not become a recipient-existence oracle. Limit pagination and avoid raw provider errors, row data, user IDs in logs, credentials, headers, messages and target email values. Set no-store on pending/claim/reveal/cancel responses and errors.
- **Tables/storage:** keep restrictive grants and RLS for client roles; never grant raw `capsules.body` or pending recipient data. The service role bypasses RLS; the security model relies on the backend and RPC authorization, and a compromised service key bypasses this model. No media is in scope; private Storage policies and denial tests must be designed and verified before enabling it.

## 8. Retry, idempotency and cancellation

No automatic POST retry is safe by default. Proposed create idempotency: a high-entropy client-generated key scoped to the authenticated sender and direct-create operation, reserved atomically with creation and a keyed digest of a canonical request. Same key and same payload return the original safe result; same key with different payload is a generic conflict. Store no raw body in an idempotency ledger, never use the key as an invitation credential, enforce unique constraints and bounded retention, and explicitly design keyed-digest secret management. This mechanism is a proposed dependency; until verified, an uncertain create must direct the user to inspect the sender list rather than blindly repeat.

Claim may be idempotent only for the **same already-bound user** and unchanged eligible capsule; it must never bind a different user, revive an expired/revoked unclaimed invitation or disclose a claim to another actor. Define repeat behavior explicitly after email change; UUID-bound access does not itself authorize a fresh claim by a changed email. Cancellation may return the original timestamp for a repeated request from the authorized original sender even after unlock, mirroring self behavior, provided deletion/recipient disqualification rules are specified; a new cancellation must still occur strictly before unlock. Repeats must not signal recipient account existence. Any uncertainty after an interrupted POST requires an explicit user-driven refresh; no retry is automatic.

## 9. Server-enforced abuse controls — initial proposal

These are **starting limits to approve and tune**, not existing infrastructure or promises. Enforce server-side before enabling direct capsules; client timers are not controls.

| Action | Initial budget | Notes |
| --- | --- | --- |
| Direct create | 5 per sender per hour; 20 per sender per UTC day | Count attempts, including rejected target addresses. Separate global circuit breaker; generic recipient-independent result. |
| Target address | 3 direct-create attempts per normalized target per UTC day across senders | Use a keyed HMAC of canonical email, not raw email in the limiter key; respond without disclosing target-specific state. Needs secure key storage/rotation. |
| Pending discovery | 30 per authenticated user per hour | Bounded page size and query cost; no arbitrary-email parameter. |
| Claim | 10 per authenticated user per hour | Count failed and successful attempts; add a coarser per-IP guard only at a trusted proxy with correctly configured client-IP handling. |

Use an atomic shared limiter, such as a private PostgreSQL-backed admission ledger with atomic counters, protected from client roles, or a separately approved equivalent shared store. No such limiter currently exists. Do not rely on process-local counters or pretend an API gateway is already deployed. Separate a short, committed admission transaction from the business RPC so denied claims and error paths consume quota even if the business transaction rolls back; both must be enforced by the trusted API path before the privileged operation, with failure of the limiter **fail closed**. Direct service-role calls are a privileged bypass and must be restricted operationally and tested. Bound ledger retention and target-hash access, define secret rotation and clock/window behavior, and avoid raw email logs. Consider sender reputation, verified adult consent, recipient block/report and support before beta. A 429 must not identify whether a target exists or disclose another sender's activity; fixed response and retry guidance need privacy review.

Create admission/idempotency ordering must avoid charging harmless same-key replays unexpectedly while preventing attackers from using idempotency to bypass budgets. Design and test this explicitly. A rate-limit admission committed just before an RPC may consume quota even if the operation never starts; this conservative tradeoff should be documented. Independently committed admission does not make capsule/job creation transactional.

## 10. Test plan and privilege verification

**SQL security and regression:** test all state constraints and old self rows, no tokens in direct pending rows, seven-day boundary before/at/after, null/invalid IDs, self-addressed direct capsule denial, unbound historical claim denial, exact projections, no title/body in pending inbox, sender cannot reveal, wrong-user failures, repeat semantics, generic errors, RLS and effective permissions. Run existing self create/reveal/cancel SQL and API regressions unchanged in intent. Fixtures must be synthetic and isolated, and tests must not return private rows.

**Identity and lifecycle:** verify unconfirmed sender/recipient, pending email change, confirmation completion, current email reassignment, stale JWT, different account with same former address, account deletion, UUID-bound access after email change and deletion/recreation. Test claim at exactly expiry, already-claimed repeat, revoked/expired/cancelled/deleted denial and late confirmation. Confirm provider-specific state through a controlled isolated setup; do not simulate a schema and infer actual Auth behavior.

**Two-session race tests:** execute each with independent trusted connections, explicit transactions, deadlines and disposable fixtures: claim versus claim; claim versus cancellation and revocation in both orders; claim/discovery versus Auth email change and account deletion; claim across seven-day expiry while waiting; reveal versus cancellation/deletion and unlock boundary; sender/profile deletion versus creation; repeat/rollback paths; rate-budget races and idempotency-key collisions. Observe post-commit state, no early body, and fail-closed timeout/deadlock/serialization results. Verify every relevant writer uses the same lock order. External notifications, if later enabled, require job lease/send races separately.

**Effective security:** in an isolated environment inspect `pg_proc` owner, security-definer flag, search path, effective EXECUTE privileges including `PUBLIC`, role inheritance/default grants, schema USAGE and service-role memberships; actually attempt RPC execution and direct SELECT/INSERT/UPDATE as `anon` and `authenticated`. Verify effective table grants/RLS and actual PostgREST routing/read-write transaction behavior. Do not assume source migration declarations prove current deployment. Storage policies and direct object access require separate testing before media.

**API and integration:** mocked JWT signature/issuer/audience/expiry and current-email authority; prevent subject/email/owner overrides, body/title leakage and sensitive logs; test 401/404/422/429/503 sanitization, no-store, idempotency and no automatic retries. Run live cross-account tests only against separately authorized disposable accounts and fixtures: sender, intended recipient, unrelated account and changed/deleted identity; verify direct client DB/storage access fails and self-capsules remain functional. Do not contact Supabase or run migrations during this design task.

## 11. Blocking verification and decisions before executable migration

1. **Supabase Auth authority:** confirm which fields establish the current confirmed email during pending email changes, their update/reassignment rules, and whether transactional locks actually serialize all email-change and deletion paths. Verify target roles can safely and minimally access that data. The repository does not prove these guarantees.
2. **Lock order and provider internals:** verify FK cascades, profile triggers, existing 0003/0004/0005, Auth change/deletion paths and chosen limiter implementation do not invert the proposed order. Reconcile any incompatibility before coding.
3. **Reassignment and retention:** explicitly accept or reject verified-mailbox-control-at-claim for an address reassigned during seven days. Approve claimed access after email changes, account deletion retention and optional pending revoke/reissue behavior.
4. **Deployment state:** inspect existing self, token-backed and unbound rows before adding discriminators; identify actual check names and effective privileges. No legacy row may be silently reclassified. Confirm separate development and beta data.
5. **Abuse and idempotency:** approve limits, limiter store and trust boundaries, HMAC secret handling, retention, denial behavior, idempotency semantics and block/report requirements. No enforcement infrastructure presently exists.
6. **Metadata and operations:** approve whether claimed titles are visible, sender-safe listing and any consent notifications; confirm expiry UX and rate-limit response privacy. Finalize concurrency and isolation evidence required before any live deployment.

Recommended next step: review this design and resolve these blockers; only then separately scope an executable migration and isolated test suite. No application, schema, deployed data or service was changed by this design.
