# Phase 4 #014I-3: per-invitation encryption evaluation

## Decision and implementation

Per-invitation HKDF keys are a defensible dormant design under a strong operating-system CSPRNG and independent fresh randomness for every attempt. They avoid a durable global **nonce allocator**; they do not eliminate key management, restore/clone controls, probabilistic collisions or the need for independent security review. The public creation stub remains unavailable and no route or email delivery is wired. The `DIRECT_CAPSULES_ENABLED` default remains false, and 0006's `CHECK (false)` remains intact. No production credentials, hosted Supabase, Android changes, commit or push were used.

The new helper draws a fresh 32-byte random salt and independent 12-byte random GCM nonce for each encryption attempt. HKDF-SHA256 derives a 32-byte AES key from a server-only root, the salt, a versioned domain string, environment UUID, explicit key version, and the job, invitation and capsule UUIDs. The salt is nonsecret. Associated data includes a separate versioned domain, those identifiers, the key ID, normalized recipient email and salt. [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869) specifies HKDF's nonsecret salt and context-specific info; [NIST SP 800-38D](https://nvlpubs.nist.gov/nistpubs/legacy/sp/nistspecialpublication800-38d.pdf) sets a uniqueness requirement for GCM key/IV pairs. Applying them this way and the risk analysis below are this draft's design, not a certification of the implementation.

One `PerInvitationEncryptor` instance allows only one encryption attempt, including failed attempts, under a process lock; ordinary copying is rejected. It creates exactly one invitation secret and digest and never returns its derived key. Separately instantiated helpers do not share a registry: their independence depends on fresh random values and unique context. The private creation test seam generates IDs, encrypts once, and passes the digest, key ID, salt, nonce and ciphertext to one atomic creation RPC. It never retries and returns only validated metadata. The caller must still supply a verified JWT subject, while database time and owner eligibility are checked in 0010. The public stub does not invoke this seam.

Draft 0010 now stores the salt with the job and in the retained collision record, with length checks, a matching foreign key, and uniqueness per key ID for committed salt and nonce values. This conservative nonce uniqueness check can reject a harmless equal nonce under distinct derived keys. A duplicate committed salt also fails and rolls back the entire creation. These checks occur **after encryption** and cover only the current database state; they cannot prevent duplicate encryption after rollback, restore, across independent databases or before the check. The draft's RPC signature changed; this is not a migration for any database where the earlier draft was already applied. Do not apply it to a hosted database.

The previous shared-key/random-nonce and nonce-lease helpers are preserved as legacy test primitives, not part of the new creation seam and not a production alternative. Existing uncommitted work was retained.

## Collision, retry and lifecycle analysis

- With independently uniform 256-bit salts, the birthday bound for any salt collision among `q` attempts is approximately `q(q-1)/2^257`; for `q = 2^32` it is below `2^-193`. A salt collision alone does not repeat the derived key when any included UUID differs. Different HKDF inputs can theoretically yield the same 256-bit output; uniqueness is probabilistic, not mathematical. The independent random nonce adds protection if a derived key nevertheless repeats. These bounds assume independent, uncompromised randomness and standard cryptographic assumptions; they are not measurements or a guarantee.
- Simultaneous operations use separate helpers and operating-system random draws. A process-level one-use lock blocks reuse of one instance, but cannot detect duplicate objects or force a CSPRNG to be independent across machines. Forked, snapshotted or cloned systems must be proven to obtain fresh entropy before encryption. If independence cannot be established, fail closed and rotate to an independently provisioned root/version before resuming; do not assume a database restore fixes random-generator state.
- Rollback may remove the SQL collision record after an encryption attempt. A subsequent attempt must use a fresh helper and fresh random values, never reuse a salt/key/nonce tuple. Database restore can erase committed collision records; risk remains bounded only when new random draws are independent of the pre-restore draws. If that cannot be assured, stop writes and rotate the key under an operationally enforced restore procedure.
- An RPC timeout can mean commit or rollback. The prototype makes no automatic retry. A later new attempt must use a new helper, salt, nonce and IDs, but may still create a duplicate logical invitation if the first attempt committed. Resolve ambiguous outcomes with a separately designed idempotency/reconciliation protocol before activation; repeating encryption is not a safe way to discover the outcome.
- Each environment must have its own isolated root and globally unique, immutable environment UUID; key versions must never be rebound to different root material. Derivation also separates distinct environment UUIDs and versions if a root is accidentally copied, but cannot detect duplicated environment IDs or enforce independent root provisioning. Store old roots securely as decrypt-only until outstanding jobs and retention requirements expire; rotation must be tested before activation. A root compromise exposes jobs derived from it.
- Re-encrypting the same key with a repeated GCM nonce is unsafe. One-shot objects prevent ordinary reuse of one instance, but the scheme cannot absolutely prevent distinct instances from repeating all random/context inputs or callers from bypassing the helper. Independent random nonces are defense in depth, not permission to reuse a derived key. Exceeding the intended one-encryption-per-key policy or uncertain entropy must stop creation.

## Remaining limitations and next step

There is no managed root-key provider, key registry, restore/clone entropy verification, real RPC transport or delivery worker. There is no end-to-end Python-to-PostgreSQL encrypted fixture yet. Database SQL cannot prove ciphertext matches a submitted digest; future delivery must decrypt/authenticate and verify the digest, then recheck cancellation, deletion, expiry, revocation and claiming. Python memory, external logging, WAL and backup retention require separate controls. The existing claim draft's bearer capability does not prove the claimant's current email matches the intended mailbox; identity policy, managed Auth/session behavior, production grants and abuse controls remain blockers.

**Next task:** independently review the per-invitation construction and document a concrete root-key provisioning, rotation, restore/clone entropy and ambiguous-outcome protocol; then implement a local-only end-to-end fixture from the private adapter through a single SQL transaction and back through authenticated decryption, including tampered salt/context and rollback tests. Keep the public stub, feature flag, 0006 gate and delivery disabled until separately authorized.
