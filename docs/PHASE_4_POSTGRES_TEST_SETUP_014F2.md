## Roles, sessions and safe handling

- A row-locking SELECT requires schema access, SELECT on the referenced table/columns and an applicable UPDATE privilege on at least one column of the locked table under PostgreSQL privilege rules; actual managed-role grants, RLS, role membership, Auth restrictions and supported operations remain **unverified**. The disposable project's administrative database role may have the needed access, but check effective privileges through separately reviewed metadata queries after authorization. Do not grant roles, change Auth policies, modify Auth tables, expose privileged database credentials to the app, or elevate client roles to make a test pass. Failure to lock is a blocker for this method, not evidence that locks work.
- A direct connection normally provides a persistent backend session for its lifetime. Session-pooler behavior must be verified for the actual connection. A transaction pooler can pin a backend for a single explicit transaction, but cannot be assumed to preserve session state or backend identity across transactions; provider timeouts and limits may also interrupt it. Prefer direct, or verified session mode, for the controlled experiment. A persistent client socket alone does not prove a single backend survived a disconnect/reconnect. Never rely on separate SQL Editor submissions sharing a session.
- Start each console without PowerShell transcription, screen recording or shared terminal history. Do not put a password, URI, email, UUID or token in a command line. Do not enable psql query echo, query/parameter logging, HTTP body/header logging or provider diagnostic logging containing identifiers. If such logging cannot be controlled, stop. The row identifier must be supplied privately to the client for the later probe and will be sent to PostgreSQL in the query; protect it from client history and server statement/parameter logs. Disable or safely redirect psql history in each session and verify the setting using nonsensitive input before use; avoid exposing secrets through terminal scrollback. Database process memory and privileged server operators remain part of the trust boundary.
- For a later connection, use the full executable path with `--no-psqlrc` to avoid unreviewed startup scripts and `--password` to force an interactive password prompt. Supply host, port, database, role, `PGSSLMODE=verify-full`, the verified CA configuration and a short connection timeout through process-local libpq settings entered privately. Do not place a password in `PGPASSWORD`, `PGSERVICE`, a URI, PowerShell history, `.pgpass`, a service file, or a persistent environment variable. Check for inherited libpq options or credential helpers that could redirect the connection or expose values. Close both clients and clear the process-local settings afterward. An interactive prompt does not protect against a compromised workstation.

## Controlled verification checklist for a later authorized run

1. Confirm the isolated project and disposable account, current state and two controlled inboxes privately. Review the detailed test and recovery procedure in `docs/PHASE_4_AUTH_LOCK_VERIFICATION_014F.md`. Confirm a working no-lock Auth control and the configured confirmation stages. Agree on operator timing, stop conditions, no automatic retry and a safe rollback/recovery plan. Use a separate supervisor or coordinated windows to release locks promptly.
2. Establish two independent psql connections A and B to the same verified isolated database, without saving their outputs. Record only that each is connected to the intended project and that A and B are distinct. A safe later session-identity check can compare backend process IDs privately; do not record the IDs. A repeated identifier on the same live A connection supports session affinity, but does not alone prove the same transaction remains open or that a lock is held. Check after any suspected reconnection and stop if affinity is uncertain.
3. In A, explicitly begin a transaction, set bounded statement and idle-in-transaction timeouts, then take the reviewed `FOR SHARE` probe on the single known disposable User B Auth row, as described in #014F. The query returns only a matching-row count. Exactly one is required; a zero, privilege error, unknown state, session loss or unexpected logging means rollback and stop. Keep A's original transaction open. Protect the user's UUID and do not select or print the email.
4. Independently demonstrate the conflict with B: in a separate explicitly bounded transaction, request an incompatible row lock on **the same privately identified row** using a reviewed `FOR UPDATE NOWAIT` or short `lock_timeout` probe. A lock-not-available/timeout result while A is demonstrably open supports the conflict; a query failure must be classified by SQLSTATE without copying raw error details. Roll back B after the expected error so its transaction is not left aborted. B's ordinary SELECT without a row lock is not a valid conflict test.
5. Roll back A promptly, then start a fresh bounded B transaction and repeat the same lock probe. Exactly one matching row now acquired, followed by B rollback, is the release control. If B acquires the incompatible row lock while A should still hold its lock, or cannot acquire it after A is released, stop and investigate: do not call the demonstration a pass. Verify that both transactions ended; never terminate an unrelated backend. This two-database-session control demonstrates PostgreSQL row-lock behavior for the selected row, not the behavior of the Auth service.
6. In a separately authorized run, follow #014F with a fresh A transaction and the supported authenticated Auth email-change request as the concurrent operation. Test initiation and each relevant normal confirmation stage separately, alongside no-lock controls. The Auth service may use multiple transactions and is not equivalent to B. Release A within a few seconds, ideally before the existing script's 15-second HTTP timeout. A timely wait-then-proceed observation is evidence only for the specific provider operation and settings tested. A timeout or unclear pending request is an uncertain outcome; do not automatically retry.
7. On every exit, issue `ROLLBACK` on the same open client connection, close it, and verify transaction cleanup using an independently reviewed safe administrative method if the connection was lost. Server-side `idle_in_transaction_session_timeout` is a fallback, not a normal release mechanism; use separate bounded `lock_timeout` and `statement_timeout` values appropriate to each probe. Do not leave A idle indefinitely or kill existing services. An HTTP client timeout does not prove the server stopped processing. Use only the normal supported account recovery/confirmation process after an interrupted Auth request, with separate authorization as needed.

The exact SQL lock probe is in #014F; all its proposed SQL remains unexecuted. A local fake `auth.users`, an ordinary read, a sequential before/after check, or a successful one-time email change cannot establish the managed provider's transaction boundaries, all confirmation paths, account deletion, identity reassignment or race-free claiming.
