## Key and nonce strategy

The prototype requires a 32-byte root key, nonzero explicitly assigned environment UUID and explicit key version. HKDF-SHA256 derives a different 256-bit AES key for each environment/version; the full environment UUID and version form the stored key ID. This prevents accidental use of the same *derived AES key* when the same root is supplied under distinct environment UUIDs or versions. It does not prove that independently operated environments have different UUIDs, nor detect identical key material deliberately or accidentally assigned the same UUID/version. Production must independently provision and enforce immutable globally unique environment identities and isolated root keys, prevent copied configuration and verify key provenance. A changed key under an existing key ID must be prohibited by the authority, including across restores.

The proposed production nonce strategy is a durable, atomic per-derived-key allocation outside the database rollback and restore domain. Reserve before encrypting; permanently burn allocations on failures and ambiguous outcomes. Coordinate concurrent processes, enforce key-specific limits, retain decrypt-only old key versions while their jobs require them, and issue a new isolated key version after a restore whenever the allocator's monotonic state cannot be proven intact. An operator must not resume encryption with a restored key and uncertain allocator state. A database reservation in 0010 is a second collision check for committed jobs; it cannot protect a nonce allocated before a rolled-back transaction, across independent databases, or after restore. The authority described here is not implemented or verified.

`EncryptionLease` consumes one supplied nonce once per object under a process lock, including after encryption/RPC errors, and rejects ordinary copying. This is a local guard only: it cannot prevent a second lease object, another process, a forged provider, or a restore from using the same key/nonce. Supplying a lease is not evidence of a safe lifecycle. The private test seam permits synthetic leases and must not be wired into application routes. The public stub fails closed with no RPC. Before production, a separately reviewed authority and a controlled integration must replace this stub; do not interpret these helpers as production-ready key management.

## Creation prototype behavior

The private test seam accepts a canonical UUID string that a future caller must obtain from a verified JWT, revalidates the input model, obtains and consumes a trusted lease, creates three UUIDs, generates exactly one 32-byte secret, and encrypts its canonical representation using AES-256-GCM. Existing AAD binds job, invitation and capsule IDs, key ID and normalized email. The same secret produces the SHA-256 digest. The adapter sends only digest, nonce, ciphertext and identifiers, along with existing capsule fields, to a single `aftertime_create_direct_with_outbox` RPC; it never sends the raw invitation secret or encryption key. It checks one exact metadata row, the returned capsule ID and unlock timestamp, and the creation/unlock time relationship; it returns only ID and timestamps.

The adapter performs no automatic retry and sanitizes dependency and malformed-response errors. A timed-out RPC can have committed despite an error; callers must not blindly repeat a creation. It cannot authenticate the supplied UUID or prove a collaborator's behavior. The future transport must derive identity from verified authentication, avoid logging request parameters, and ensure a single RPC with no implicit retries. Application model time checks are preliminary: 0010 enforces owner eligibility and future/unlock limits against database time, and 0006 currently rejects every invitation. No real network transport is wired or tested here.

## Security limitations

No production-safe allocator, key registry, key retrieval, delivery worker or real adapter transport exists. No global key/environment uniqueness, real restore behavior or PostgREST transaction semantics were verified. Python objects, exceptions and runtime memory cannot guarantee secret erasure; external logs, telemetry and backups require separate controls. The SQL function cannot verify ciphertext/digest correspondence from an arbitrary caller; future delivery must authenticate/decrypt and compare the digest before use, and coordinate cancellation, deletion, expiry, claim and revocation. Ciphertext removal does not erase WAL or backups. The earlier bearer-secret claim draft does not prove the account's current confirmed email matches the intended mailbox; that identity rule remains an activation blocker. Real deployment grants, managed Auth/session behavior, abuse controls and rate limits remain unverified.
