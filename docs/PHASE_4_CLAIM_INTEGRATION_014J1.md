# Phase 4 #014J-1 secure invitation claim integration

## Claim and link contract

AfterTime uses the approved authenticated, single-use bearer invitation policy. A claim requires a verified JWT subject, possession of the secret, an unexpired and unclaimed invitation, and an eligible capsule and account. Possession of the secret does not prove ownership of the originally addressed mailbox. An eligible user with a forwarded or copied link can claim it. Neither the JWT email claim nor the current account email participates in the decision. Migration 0009 excludes the sender and atomically binds one eligible account, timestamps the claim and clears the digest. It checks cancellation, deletion, revocation and expiry using database state and time after taking the relevant locks.

`services/api/app/invitation_claim.py` builds and parses the local format `https://aftertime.example.invalid/invite/<capsule-uuid>#<secret>`. The reserved host is for local tests. The path contains the canonical capsule UUID. The fragment contains the canonical unpadded base64url encoding of 32 random bytes. The parser rejects alternate origins, queries, malformed paths, noncanonical encoding and oversized input. Parsing is pure. The claim adapter requires explicit confirmation before authenticating or opening a database transaction.

The adapter uses the existing JWT verifier for the signature, issuer, audience, expiry and canonical UUID subject. It makes one parameterized call to the migration 0009 RPC with the capsule UUID, verified subject and SHA-256 digest. The adapter requires a fresh, dedicated non-autocommit service connection. Only a committed success returns capsule ID, creation time and unlock time. Invalid or unknown invitations, expired, already claimed or revoked invitations, cancelled capsules and ineligible accounts share the `unavailable` outcome. A malformed result or a database error before commit returns `service_unavailable`. A failed commit acknowledgement returns `outcome_unknown` with no metadata or automatic retry. Authentication failures retain the existing generic Auth errors.

The generated URL and parsed secret use masked representations. The adapter omits raw secrets from SQL parameters, result objects and error messages. Treat the digest as sensitive in logging as well. Migration 0006, the public claim and discovery stubs, default-off direct flag and fail-closed production delivery entry point remain in place.

## Eventual web requirements

- Use an explicitly approved HTTPS origin. Keep the fragment out of request paths and queries. The landing page should read it into memory and strip it from the address bar with `history.replaceState` before loading optional content or starting navigation. Opening a link, prefetching or signing in must leave the invitation unclaimed. Claim only after an explicit authenticated action and transfer the secret in the HTTPS request body.
- Serve the landing and claim responses with `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. Exclude third-party scripts, analytics, pixels, embeds and other third-party resources from the claim page. Keep the fragment and request body out of history handoffs, persistent browser storage, error-report payloads, telemetry, session replay and server or proxy logs. Use an approved same-origin handoff and review rate limits and abuse controls before exposure.
- Client and intermediary guarantees still need verification. Links can be copied, forwarded or captured by mailbox tooling, browser extensions or screenshots. The generic outcomes avoid exposing lifecycle details through response contents. Timing and abuse resistance require separate review before public exposure. Local tests use generated JWTs and a stub Auth table. They exercise the real verifier with a mocked JWKS lookup and the copied claim function in PostgreSQL, while leaving the actual invitation table gated. They do not establish managed Auth ban, deletion or session-revocation behavior, deployed grants, or production web and proxy logging behavior.
